# 插件项目 · 测试与写作原则

> **本文件性质**：参考笔记。测试和写东西时对照用，不是待办清单。
>
> **来源**：主体转写自大项目 `projects/dsh-pet-framework/docs/LESSONS.md`（只读参考，大项目未做任何修改）。
> 每条后面标了适用性：
> `[通用]` 直接可用 · `[改造]` 按插件场景调整过 · `[本插件]` 是自己补的，大项目没有。

## 一、测试时

### 1. 判据必须能红一次 `[通用]`

一个从没失败过的测试等于没有测试。

- 写完断言，先故意让它失败一次，确认它真的在检查东西。
- 「旧行为错 → 新行为对」要能同时显示，只写 PASS 证明不了修好了。
- 注入负向样本是常规动作：传一个坏值进去，看它是不是真的拦住。

本插件的落地方式：

```js
// 先确认这条会红
await assert.rejects(() => store.setApiKey('   '))
// 再确认正常路径是绿的
assert.equal(await store.getApiKey(), 'sk-test-123')
```

### 2. 路径、命令、版本号先实测再写 `[通用]`

大项目里这条对应 14 次「记录与实际不符」。

- 写进文档的路径，先 `stat` 一次。
- 引用 commit，先 `git log` 看一眼。
- 说「还没做」，先 grep 一遍。反向也成立：说「已经做了」更要 grep。

真实例子：这一版合并时，本地 `lib/index.js` 有 vault、远程 1.1.0 有卡片模式，两边各缺一块。只凭「远程是更新的版本」就覆盖，会把 vault 丢掉；只凭「本地是最新的」就推，会把卡片模式丢掉。

### 3. 模拟数据按规范构造，不按当前实现构造 `[通用]`

拿生产文件当 fixture，测的是「当前这份文件能不能读」，测不出「格式对不对」。

本插件的做法：

- 用 `MemoryVaultStorage` 造内存仓库，不拿 `~/.dsh` 下的真文件做输入。
- 真文件那条单独放最后一条，文件不存在就跳过。

### 4. 断言平台中立 `[通用]`

Windows 是目标平台，但写死 `\` 或写死 `/` 都不对。

- 用 `path.join` 构造。
- 比对前 `normalize`。
- 能测语义就不碰真实文件系统。

### 5. 测前备份，尤其是 vault `[改造]`

大项目这条的原文是「跨后端互解会重写密钥文件，测前必须备份整个目录」。

插件这边对应：

- 动 `~/.dsh/storages/cyrene-pet/` 之前先整目录复制一份。
- `state.json.pre-vault.bak` 这类升级遗留文件，确认没问题前不要删。
- 测「解不开」的时候，要保证还能回到「解得开」的状态。

### 6. 降级是合法结果，不是失败 `[通用]`

- 没配 key 走环境变量、走 credentials 文件，是设计好的路径。
- 「拿不到余额」和「程序坏了」要分开报。
- 不要把「有兜底」记成 error，会让诊断面板长期红着。

### 7. 只测「没崩」不算测过 `[通用]`

大项目的原话：只测「没崩」不测「行为对」，会放过「降级成了错误行为」。

本插件要盯的：

- 设置页改了，标签是否还配对（`details` / `div` / `p` 数量对不上，页面会歪）。
- 卡片模式下窗口尺寸和点击穿透是否仍然生效。
- vault 解开之后，key 长度对不对、有没有被悄悄重置。

### 8. 测试资源只用本项目的 `[本插件]`

不引用大项目的文件、不依赖大项目的目录结构。

理由：大项目是只读参考，两边一旦互相引用，任何一边挪目录都会让另一边跑不起来。

## 二、写作时

### 1. 写观测到的，不写推测的 `[通用]`

措辞纪律，大项目里专门列了一节。

| 不要写 | 改成 |
| --- | --- |
| 探针未加载 | 探针未留痕 |
| 因为 X 所以失败 | 失败发生在 X 之后，原因未确认 |
| 已经修好了 | 已改动，验证方式是…… |

后半句暗含的因果，如果不是实测得出的，就不要写进去。错误结论会把下一轮引到错误方向。

### 2. 「未验」必须写原因 `[通用]`

只写「未验证」，将来会被读成「做了但没记」。

写「未验证 —— 因为当前环境没有 GUI」，读的人才知道是没做，而不是漏记。

### 3. 「预留」不能写成「已有」 `[通用]`

- 文档声明不等于代码存在。
- 字段建了但没人读，就写「待实现」，不要写「已预留」。
- 目录建了但没有调用点，就是死代码，如实说。

本插件现状里就有这种：`lib/vault/` 里 B 路线那套代码留着没调用点，写文档时要么标「未接入」，要么删掉，不能含糊。

### 4. 不写真实路径和用户名 `[通用]`

- 文档里用描述性说法：「本机用户目录」「数据目录」。
- 汇报扫描结果时最容易犯：越想说清楚扫到了什么，越容易把真值原样抄进去。
- 写完立刻再扫一遍。

### 5. 说清楚「在哪里成立的」 `[通用]`

结论对，但成立的位置不对，是最隐蔽的一类错误。

- 跑的是插件目录里的 `lib/vault`，还是部署到 `runtime/` 里的副本？
- 测的是 `~/.dsh` 下的文件，还是临时造的？

### 6. 不解释自己刚说过的话 `[本插件]`

写完就是写完了。用户没问「为什么这么写」，就不用补一段自我分析。

文档要的是可查，不是可读性表演。

## 三、这个项目自己的教训

### 1. 两边分叉时，先比对再合并 `[本插件]`

2026-10-29 合并 1.1.1 时的真实情况：

| | 本地 | 远程 main |
| --- | --- | --- |
| 版本 | 1.0.4 | 1.1.0 |
| 卡片模式 | 无 | 有 |
| `lib/vault/` | 有 | 无 |

结论：两边各有一半。先 `git diff --numstat` 量化，再按文件决定取哪边，不要按「谁版本号大」一刀切。

### 2. 页面和样式改动要验标签配对 `[本插件]`

安全须知那两个折叠块插进去之后，`details`、`div`、`ul`、`p` 的数量都要重新数一遍。HTML 不会报错，只会默默歪掉。

### 3. vault 的四条底线要一直测 `[本插件]`

- 密文里不含明文。
- 空 key 明确拒绝，不静默写入。
- 错误口令解不开。
- 篡改密文能被识别。

这四条任意一条失效，加密就等于没有。

### 4. 打包前确认版本号只在一处 `[本插件]`

`package.json`、`README.md` 的「当前版本」、下载段的 zip 文件名，三处要对得上。release 没发的时候，README 里要注明「安装包沿用上一版」。
